# 知識ベースアプリ 設計書

- 文書バージョン: 1.0
- 作成日: 2026-09-20
- ステータス: ドラフト（Phase 1 着手可）

---

## 1. 目的とコンセプト

自分専用の知識ベース。**フォルダを作らず、すべてのページをフラットに置き、ラベル（階層タグ）だけで分類・検索する。**

ページ本文は Claude Code が生成する「自己完結 HTML」。エディタは実装しない。書く行為は Claude Code との対話に外出しし、アプリは**貯めた HTML を分類・一覧・閲覧するための器**に専念する。

### 設計原則

1. **フラット構造の徹底** — 物理配置に階層を持たせない。階層は「ラベルの意味」としてのみ存在する。
2. **データはプレーンなファイル** — DB を使わない。ページは HTML、メタデータは JSON。git が履歴とバックアップを兼ねる。
3. **アプリは読み取り専用** — 書き込み（ページ生成・ラベル付与）は取り込み工程（Claude Code）の責務。アプリ側に書き込み機能を持たせない。
4. **表現の自由を殺さない** — ページの HTML には CSS / SVG / JS を許可する。そのため閲覧は iframe で隔離する。
5. **後から決められる形で作る** — 全文検索・バックリンク・RAG・デプロイは未決。それらを後付けできる境界だけ先に引く。

## 2. 壁打ちで確定した要件

| 利用形態 | 自分だけ。当面ローカル、将来デプロイ |

## 3. 全体アーキテクチャ

```
┌──────────────────── 書く（アプリ外） ────────────────────┐
│  Claude Code                                              │
│   1. npm run new  → slug 採番・ページ雛形作成              │
│   2. artifact-design の作法で index.html を執筆            │
│   3. labels.json を読みラベル候補を提案 → 本人が確定       │
│   4. meta.json 更新 / 新ラベルを labels.json へ登録        │
└───────────────────────────┬───────────────────────────────┘
                            │ ファイル書き込み + git commit
                            ▼
┌──────────── コンテンツ（単一の真実 / git 管理下）──────────┐
│  content/pages/<slug>/index.html   ページ本文（自己完結）  │
│  content/pages/<slug>/meta.json    タイトル・ラベル・日付  │
│  content/labels.json               ラベルレジストリ        │
└───────────────────────────┬───────────────────────────────┘
                            │ prebuild スクリプト
                            ▼
┌──────────────── 生成物（git 管理外）─────────────────────┐
│  src/generated/index.json   全ページのメタ + ラベルツリー  │
│  public/pages/<slug>/…      本文 HTML と添付のコピー       │
└───────────────────────────┬───────────────────────────────┘
                            │ next build（output: export）
                            ▼
┌──────────────── 読む（Next.js 静的アプリ）───────────────┐
│  /            トップ：左ラベルツリー + 右ページ一覧        │
│  /labels/…    ラベルで絞り込んだ一覧                      │
│  /p/<slug>    ページ詳細（本文を iframe で隔離表示）       │
└───────────────────────────────────────────────────────────┘
```

**要点:** アプリは `src/generated/index.json` しか読まない。本文 HTML はアプリの React ツリーに入らず、`public/pages/` から iframe で読み込まれる。この分離により、本文にどんな JS が入っていてもアプリ本体は壊れない。

`.gitignore` に `src/generated/`, `public/pages/` を追加する。生成物をコミットしないことで、`content/` の差分だけが履歴に残る。

### ページディレクトリ方式を選ぶ理由

Claude Code が生成するのは `<!doctype html>` から始まる完結した文書であり、Markdown の frontmatter 本文に押し込むのは不自然（エスケープ事故とエディタ表示の崩れを招く）。ディレクトリ方式なら、

- `index.html` を**そのままブラウザで開いて確認できる**（アプリのビルド不要）
- メタデータが本文と混ざらないので、スクリプトからの読み書きが安全
- 添付ファイル（U4）を相対パスで同居させられる
- iframe 配信時も相対パスがそのまま解決される

## 5. データモデル

> **この節と §6 は `docs/label-spec.md`（v2・確定）に上書きされている。**
> `labels: string[]` は廃止され、`mainLabel: string` + `subLabels: string[]`（`schemaVersion: 2`）になった。
> 実装は v2 に移行済み。以下は v1 の記録として残す。

### 5.1 `content/pages/<slug>/meta.json`

```json
{
  "schemaVersion": 1,
  "id": "20260920-a3f2",
  "title": "SQLite FTS5 の基本と日本語対応",
  "summary": "FTS5 の仮想テーブル設計と、日本語を N-gram で引くための tokenizer 設定。",
  "labels": ["技術/SQLite", "技術/全文検索", "形式/調べ物"],
  "createdAt": "2026-09-20",
  "updatedAt": "2026-09-20",
  "visibility": "private",
  "links": [],
  "source": {
    "kind": "claude-code",
    "note": "公式ドキュメントと手元検証をもとに生成"
  }
}
```

| フィールド | 必須 | 説明 |
|---|---|---|
| `schemaVersion` | ○ | スキーマ変更時の移行判定用。現在 `1` |
| `id` | ○ | slug と同じ。ディレクトリ名と一致すること（ビルド時に検証） |
| `title` | ○ | 表示用タイトル。**こちらが正**（HTML の `<title>` は補助） |
| `summary` | ○ | 1〜2文。一覧のプレビューと、将来の検索・RAG の対象 |
| `labels` | ○ | 正規化済みラベルパスの配列。1件以上。目安 3〜7件 |
| `createdAt` / `updatedAt` | ○ | `YYYY-MM-DD` |
| `visibility` | ○ | `private` 固定（U5 で公開を扱うときに `public` を追加） |
| `links` | – | 他ページの id 配列。**Phase 4 のバックリンク用に器だけ用意**。Phase 1 では空配列 |
| `source` | – | 出自メモ。後から「これは何を見て書いたか」を追える |

### 5.2 `src/generated/index.json`（ビルド生成物）

```json
{
  "generatedAt": "2026-09-20T09:00:00.000Z",
  "pages": [
    {
      "id": "20260920-a3f2",
      "title": "…",
      "summary": "…",
      "labels": ["技術/SQLite"],
      "createdAt": "2026-09-20",
      "updatedAt": "2026-09-20"
    }
  ],
  "labels": [
    { "path": "技術", "count": 12, "selfCount": 0, "children": ["技術/SQLite"] },
    { "path": "技術/SQLite", "count": 3, "selfCount": 3, "children": [] }
  ]
}
```

- `count` は子孫を含むページ数、`selfCount` はそのラベルが直接付いたページ数。ツリー表示で「親だけ選んでも子が全部拾える」ことを数字で示すために両方持つ。
- 本文 HTML は index.json に含めない（サイズ爆発を防ぐ）。全文検索を入れる際は別ファイル（`search-index.json`）を遅延ロードする。

## 6. ラベル設計

> **この節は `docs/label-spec.md`（v2・確定）に上書きされている。**
> 主題軸（`技術` / `仕事` / `生活`）は廃止し、メインラベルの第一階層は対象アプリ（`Blender` / `After Effects`）、
> 第二階層は公式ドキュメントのサイドバー準拠の固定リストになった。正規化ルール §6.2 の例外は label-spec.md §7.3 を参照。
> 実装は v2 に移行済み。以下は v1 の記録として残す。

フォルダを作らない代わりに、分類の負荷はすべてラベルが背負う。ここが本アプリの心臓部。

### 6.1 形式

- **スラッシュ区切りの階層パス**: `技術/SQLite`、`仕事/提案書/構成`
- 1ページに複数付与。**階層が異なる軸を並べて付けるのが基本形**（例: `技術/SQLite` + `形式/調べ物`）
- 推奨深さは **最大3段**。4段目が欲しくなったら、それは軸の切り方を間違えているサイン

### 6.2 正規化ルール（`lib/labels.ts` で実装し、ビルド時に検証）

1. Unicode NFKC 正規化（全角英数・半角カナのゆらぎを吸収）
2. 前後の空白を除去。各セグメントの前後空白も除去
3. 先頭・末尾のスラッシュを除去。連続スラッシュは1つに畳む
4. 空セグメントを禁止
5. セグメント内で禁止する文字: `/`（区切り専用）、`,`（将来のクエリ区切り）、制御文字
6. 空白は許可するが**非推奨**（`全文 検索` ではなく `全文検索`）。ビルド時に警告
7. ラテン文字のみのセグメントは**小文字に統一**（`SQLite` のような固有名詞は §6.4 の別名で吸収）

違反があればビルドを失敗させる。「なんとなく似たラベル」が増殖するのを機械で止めるのが目的。

### 6.3 階層の意味論

- `技術/SQLite` を登録すると、**親 `技術` は暗黙に存在する**（親を明示的に付与する必要はない）
- 絞り込みは**前方一致（子孫を含む）**。`技術` を選ぶと `技術/SQLite` のページもヒットする
- 「親そのものが付いたページだけ」を見たい場合は、UI に「直下のみ」トグルを置く（Phase 2）

### 6.4 `content/labels.json`（ラベルレジストリ）

ラベルは自由記述にしない。**レジストリに登録されたラベルだけを使う**。これが AI 提案の一貫性を担保する。

```json
{
  "schemaVersion": 1,
  "labels": [
    {
      "path": "技術/SQLite",
      "description": "SQLite 本体と拡張機能に関する知識",
      "aliases": ["sqlite", "SQLite3"]
    },
    {
      "path": "形式/調べ物",
      "description": "調査してまとめた結果。あとで参照する前提のもの"
    }
  ],
  "renamed": {
    "技術/sqlite": "技術/SQLite"
  }
}
```

- `description` は**AI がラベルを選ぶための判断材料**。ここを書かないと提案精度が落ちる。必須運用とする
- `aliases` は表記ゆれの受け皿。Claude Code が別名で提案してきても正規パスに寄せられる
- `renamed` は改名履歴。古い meta.json が残っていてもビルド時に自動で読み替え、警告を出す

### 6.5 推奨する初期の軸

強制はしないが、最初にこの3軸を置くと迷いが減る。

| 軸 | 用途 | 例 |
|---|---|---|
| `技術/…` `仕事/…` `生活/…` など**主題** | 「何についての知識か」 | `技術/SQLite`, `仕事/提案書` |
| `形式/…` | 「どういう性質の記述か」 | `形式/調べ物`, `形式/手順`, `形式/読書メモ`, `形式/アイデア` |
| `状態/…` | 「どのくらい信頼できるか」 | `状態/確定`, `状態/検証中`, `状態/要更新` |

### 6.6 ラベル運用ツール（`scripts/label-ops.ts`、Phase 2）

フラット + ラベル運用は、**必ずラベルが増えすぎて破綻しかける**。その時点で手作業に頼らないよう、最初から道具を用意する。

- `rename <from> <to>` — 全 meta.json を書き換え、`renamed` に履歴を追記
- `merge <from> <to>` — 統合。重複ラベルを除去
- `unused` — レジストリにあるが 0 件のラベルを列挙
- `orphan` — meta.json にあるがレジストリ未登録のラベルを列挙
- `stats` — ラベルごとの件数、深さ分布、1ページあたり平均ラベル数

## 7. ページ HTML の規約

Claude Code は **artifact-design スキルの作法で HTML を書き、Artifact として公開する代わりに `content/pages/<slug>/index.html` に保存する。**

### 7.1 必須要件

1. **自己完結** — 外部ホストへの参照を一切含めない（CDN、Web フォント、外部画像、fetch / XHR / WebSocket）。CSS と JS はインライン、画像は data URI かページディレクトリ内の相対パス
2. **完結した文書** — `<!doctype html>` から `</html>` まで自分で書く（Artifact 公開時と違い、外側の骨組みは付与されない）
3. **`<title>` を入れる** — タイトルの正は meta.json だが、HTML 単体で開いたときの識別に必要
4. **テーマ対応** — `:root` に明色パレットを定義し、`@media (prefers-color-scheme: dark)` で暗色を上書き。`body` に必ず不透明な背景色を指定する（透明だと iframe 越しに親の色が透ける）
5. **レスポンシブ** — 横幅は相対単位。表・図・コードブロックは `overflow-x: auto` の内側でスクロールさせ、**文書自体を横スクロールさせない**
6. **高さ通知** — 本文の高さを親に伝えるため、ビルド時に高さ通知スニペットを注入する（§7.3）。ページ側で書く必要はない

### 7.2 許可されること

JS・SVG・Canvas・アニメーション・インタラクティブな図解は自由。iframe で隔離されているため、本文の JS がアプリを壊すことはない。

### 7.3 ビルド時の加工（`scripts/build-index.ts`）

`content/pages/` → `public/pages/` へコピーする際に、以下を注入する。

1. **高さ通知スニペット** — `ResizeObserver` で `document.documentElement.scrollHeight` を監視し、変化を `postMessage` で親に送る。親（`PageFrame.tsx`）が受け取って iframe の高さを合わせる
2. **CSP の `<meta>`** — `default-src 'none'; img-src 'self' data:; style-src 'unsafe-inline'; script-src 'unsafe-inline'; font-src data:` 相当。**外部通信を機械的に遮断する**。「自己完結」を規約の努力目標ではなく強制にするための仕掛け

注入はコピー先に対してのみ行う。`content/` 側の原本は汚さない。

### 7.4 iframe の設定（`PageFrame.tsx`）

```html
<iframe
  src="/pages/20260920-a3f2/index.html"
  sandbox="allow-scripts"
  loading="lazy"
  title="{meta.title}"
/>
```

`allow-scripts` は付けるが **`allow-same-origin` は付けない**。両方を同時に付けると sandbox が実質無効化される。この組み合わせで、本文の JS はユニークオリジンに閉じ、アプリの DOM・localStorage・Cookie に触れない。

## 8. 取り込み（書く）ワークフロー

アプリ外の手順。U1 が決まればここだけ差し替える。

### 8.1 手順

```bash
# 1. ページの器を作る（slug 採番 + meta.json 雛形 + index.html 雛形）
#    メインラベルは必須。公式ドキュメントのどのセクションに載っているかで決める
npm run new -- --title "ベベル後の編集が大変な問題" --main "Blender/モデリング"
#    → content/pages/20260920-a3f2/ が生成される
#    --main を省くと、選べるメインラベルの一覧を出して失敗する
```

2. **本文執筆（Claude Code）** — artifact-design スキルを読み、§7 の規約に沿って `index.html` を書く
3. **サブラベル提案（Claude Code）** — `content/labels.json` を読み、`description` を手掛かりに既存ラベルから **3〜7件の候補**を提示する。
   - メインラベルは §1 の固定リストから選ぶだけなので、提案の対象は**サブラベル**
   - 既存ラベルで表せるなら**新規ラベルを作らない**。これを既定の態度とする
   - 新規を作れるのは、実質 **メイン体系の3段目**（`Blender/モデリング/ベベル` など）だけ。第二階層は固定リストなので増やさない
4. **本人が確定** — 採否と修正を決める。確定後、Claude Code が `meta.json` の `subLabels` を更新し、新規の3段目ラベルを `labels.json` に `description` 付きで追記する
5. **確認** — `npm run dev` で一覧と詳細を確認（`index.html` を直接ブラウザで開く確認でも可）
6. **コミット** — `git commit`。履歴とバックアップは git が担う

### 8.2 `npm run new` の仕様

- slug = `YYYYMMDD` + `-` + base36 4文字（衝突時は再生成）
- 引数: `--title`（必須） / `--main`（必須） / `--sub`（0個以上、繰り返し可）
- `--main` はレジストリと照合し、2段でない・未登録・補助軸ならその場で失敗する（別名で書けば正規パスに寄る）
- `meta.json` を雛形で作成（`summary` は空、日付は当日）
- `index.html` に §7 準拠の最小テンプレート（テーマトークン定義済み）を配置
- `subLabels` が空のページはビルド時に**警告**（エラーにはしない。書きかけを許容する）。
  一方 `mainLabel` は**無いとエラー**なので、器を作る時点で決めさせている

### 8.3 Claude Code 向けチェックリスト

保存前に確認する項目。将来これをプロジェクトのスキル / CLAUDE.md に落とす。

- [ ] 外部ホストへの参照がゼロ
- [ ] `<title>` がある
- [ ] 明色・暗色の両方で読める
- [ ] 横幅 375px で横スクロールが出ない
- [ ] `meta.json` の `title` / `summary` / `mainLabel` / `subLabels` が埋まっている
- [ ] メインラベルは**公式ドキュメントのどこに載っているか**で決めた（自分の感覚で決めていない）
- [ ] サブラベルは既存レジストリから選んだ（3段目を新設したなら理由を説明した）
- [ ] `id` とディレクトリ名が一致している

### 8.4 夜間の自動取り込み

Obsidian（`iCloud~md~obsidian/.../Blender/` の `Q&A` / `テクニック` / `知識`）に増えた md は、毎日 0:10 に launchd が
`scripts/import-daily.sh` を呼び、上の手順 1〜6 を無人で回して push する。詳細は **docs/daily-import.md**。

手順4（本人がラベルを確定する）だけは無人化できないため、自動実行では次のように代替している。

- 置かれているフォルダと frontmatter の `tags` を手掛かりにし、本文と突き合わせてラベルを決める
  （フォルダは `Blender/Q&A` / `Blender/テクニック` / `Blender/知識` に対応。この3つは互いに排他）
- 新規ラベルは作らせない。サブラベルは既存レジストリから選ぶだけ
- メインラベルを決めきれない md は**ページ化せず見送り**、理由をログに残す
- 見送った md は本人が書き直せば自動で再挑戦の対象に戻る

ページ化済みかどうかは `meta.json` の `source.file`（取り込み元からの相対パス。例 `Q&A/Q&A_xxx.md`）で判定する。

## 10. 非機能要件

### 10.1 技術スタック

| 項目 | 選定 | 理由 |
|---|---|---|
| フレームワーク | Next.js（App Router）+ TypeScript | 指定。`output: 'export'` で完全静的化 |
| ビルド出力 | `output: 'export'`, `trailingSlash: true` | サーバー機能を一切使わない。どこにでも置ける |
| スタイル | Tailwind CSS | アプリ側 UI のみ。本文 HTML には適用しない（本文は自前の style を持つ） |
| データ層 | JSON ファイル + ビルド時生成 | DB なしの指定。`content/` が単一の真実 |
| スクリプト | tsx で実行する TypeScript | アプリと型を共有する（meta.json の型定義を一箇所に置く） |
| 履歴・バックアップ | git | 別途のバージョン管理機能を実装しない |

Server Actions、API Routes、動的ルートのフォールバック、`next/image` の最適化（`unoptimized: true` にする）は使えない。この制約を守る限り、生成物は素の静的ファイル群になる。

### 10.2 規模の想定と性能

| 項目 | 想定 | 対策 |
|---|---|---|
| ページ数 | 〜1,000（数年分） | `index.json` はメタのみで 1,000件 ≒ 300KB 程度。許容範囲 |
| ラベル数 | 〜200 | ツリー描画は問題なし。200 を超えたら §6.6 の `stats` で整理 |
| 1ページの HTML | 〜500KB（図解込み） | iframe の `loading="lazy"` で一覧時は読み込まない |
| ビルド時間 | 1,000ページで数十秒 | 静的生成するのはラベルページと詳細ページ。本文はコピーのみ |

ページ数が 2,000 を超えたら `index.json` の分割と一覧の仮想スクロールを検討する（Phase 2 以降の課題として記録）。

### 10.3 セキュリティ・公開範囲

現状は**公開しない**前提。ただし以下は Phase 1 から入れる。

- `public/robots.txt` に `User-agent: * / Disallow: /`、各ページに `noindex` メタ — 将来うっかり公開しても検索に載らないようにする
- 本文 iframe は `sandbox="allow-scripts"`（`allow-same-origin` なし）
- 注入 CSP で本文からの外部通信を遮断（§7.3）— 生成 HTML が意図せず外部を叩くのを防ぐ
- `visibility` フィールドを最初から持つ — 公開時に「公開分だけ出力」へ拡張できる

将来デプロイする場合（Phase 5）は、静的ホスティングのまま **Cloudflare Pages + Cloudflare Access**（または同等の前段認証）を第一候補とする。アプリ側に認証を実装しないため、ホスティング層で閉じるのが最も整合する。

### 10.4 ビルド時検証（`build-index.ts` が失敗させる条件）

「壊れたコンテンツが静かに混ざる」のを防ぐため、以下はビルドエラーにする。

- `meta.json` が必須フィールドを欠く / `id` とディレクトリ名が不一致
- `index.html` が存在しない
- ラベルが正規化ルール（§6.2）に違反
- ラベルが `labels.json` 未登録（`renamed` で解決できない）
- slug の重複

警告（ビルドは通す）にするもの: `labels` が空、`summary` が空、ラベル内の空白、深さ4段以上、レジストリにあるが 0 件のラベル。

## 11. 実装フェーズ

### Phase 1 — MVP（貯めて引き出せる最小形）

1. Next.js + TypeScript + Tailwind の初期化、`output: 'export'` 設定
2. `content/` のスキーマと型定義（`meta.json` / `labels.json`）
3. `scripts/new-page.ts`（slug 採番・雛形生成）
4. `scripts/build-index.ts`（検証・`index.json` 生成・`public/pages/` 同期・高さ通知と CSP 注入）
5. `lib/labels.ts`（正規化・ツリー構築・前方一致絞り込み）
6. トップ画面（ラベルツリー + 一覧 + AND 絞り込み）
7. ページ詳細（iframe + 高さ自動調整 + メタヘッダ）
8. `/labels/[...path]` の静的生成
9. `robots.txt` / noindex
10. 取り込み手順を CLAUDE.md（またはプロジェクトスキル）に記述 — §8.3 のチェックリストを含む

**Phase 1 の完了条件:** Claude Code が 3 ページ作り、ラベルで絞り込んで閲覧でき、`npm run build` が静的出力に成功する。

### Phase 2 — 運用に耐える形にする

- `scripts/label-ops.ts`（rename / merge / unused / orphan / stats）
- OR 絞り込み、「直下のみ」トグル、ラベル未設定ページの抽出ビュー
- 一覧のサムネイル（任意 / 重いなら見送り）
- 一覧の仮想スクロール（ページ数が増えたら）

### Phase 3 — 全文検索（U2）

- ビルド時に本文からテキストを抽出し `search-index.json` を生成
- クライアント側検索（minisearch 等）。日本語は N-gram で分割
- 索引は遅延ロードし、初期表示を重くしない

### Phase 4 — ページ間リンクとバックリンク（U2）

- `meta.json` の `links` を使い、ビルド時に逆引きを算出
- 詳細画面に「このページを参照しているページ」を表示
- 本文 HTML 内のリンク記法を `/p/<slug>` に解決する規約を決める

### Phase 5 — デプロイとアクセス保護（U5）

- Cloudflare Pages への静的デプロイ
- Cloudflare Access 等による前段認証
- `visibility` に応じた出力フィルタ（公開分のみビルドする経路）

### Phase 6 — AI 検索（U2、必要になったら）

- ページ単位の埋め込みをビルド時に生成
- 静的ホスティングのままでは埋め込み生成に外部 API が必要。**ここで初めて「DB なし・完全静的」の前提を見直す**。それまでは前提を崩さない

## 12. この設計のリスクと対処

| リスク | 内容 | 対処 |
|---|---|---|
| ラベル体系の崩壊 | フォルダがない分、ラベルが増えすぎると何も見つからなくなる | レジストリ必須化（§6.4）、`description` 必須、新規を作らない態度を既定に、Phase 2 の運用ツール |
| 本文 HTML の品質ばらつき | 生成のたびに見た目・構造が変わり、一覧が雑多になる | §7 の規約とテンプレート、§8.3 のチェックリスト、テーマトークンの共通化 |
| 検索できない期間 | Phase 3 まで全文検索がない。ラベルだけで引けるか未検証 | `summary` を必須にし、一覧で本文を読まずに判断できるようにする。50 ページ前後で運用を振り返り、Phase 3 の優先度を決める |
| エディタがないことの不便 | 誤字修正のような小さな直しでも Claude Code を起動する必要がある | `index.html` は素のファイルなので任意のエディタで直接直せる。これを正式な手段として認める（アプリに編集機能は作らない） |
| 静的前提の限界 | Phase 6 で前提と衝突する | Phase 6 到達時点で改めて設計判断する。それ以前に DB を持ち込まない |
