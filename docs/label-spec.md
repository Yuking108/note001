## 1. 変わらない原則

| 種別 | 1ページあたりの個数 | 必須 |
|---|---|---|
| **メインラベル** | **ちょうど 1 つ**（0 個も 2 個以上も不可） | ○ |
| **サブラベル** | **0 個以上、複数可** | – |

メインラベルは「フォルダを作るとしたら、このページはどこに置くか」。サブラベルは「他のどんな切り口からも引きたいか」。ここは v1 から変更しない。

## 2. 再考の結論（v1 からの変更点）

**メインラベルの軸を、自分で考えた主題軸から「アプリの公式ドキュメントの構造」に差し替える。**

| | v1（破棄） | v2（本仕様） |
|---|---|---|
| 第一階層 | `技術` / `仕事` / `生活` を自分で定義 | **`Blender` / `After Effects`**（対象アプリ） |
| 第二階層 | 主題を自分で切る（`技術/SQLite` など） | **公式ドキュメントのサイドバー準拠**（`Blender/モデリング` など） |
| 階層数 | 1〜3段の自由 | **ちょうど2段に固定** |
| 語彙の増え方 | ページを書くたびに増える | **最初に全部登録して、以後増やさない** |

### なぜこう変えるか

1. **分類の正解を外部に置ける。** 「ベベルの話はモデリングか、それともモディファイアか」で悩まない。公式マニュアルのどのページに書いてあるかを見れば決まる。自分で軸を発明しないぶん、判断が毎回ぶれない。
2. **増殖しない。** 第二階層は公式サイドバー由来の固定リスト。ページが増えてもラベルは増えない。`docs/design.md` §11 が最大リスクに挙げた「ラベル体系の崩壊」に対して、レジストリ必須化より強い歯止めになる。
3. **探し方が公式ドキュメントと一致する。** 半年後に「あれは AE のどこの機能だったか」を思い出すとき、知識ベースと公式ヘルプで同じ場所を探せる。
4. **AI の提案精度が上がる。** 候補が固定リストなので、Claude Code は「既存に似たものを作る」余地がない。

### 引き換えに失うもの（承知のうえで受け入れる）

- **アプリに紐づかない知識を置けない。** 既存の3ページ（SQLite・HTML・note001）はこの体系に入らない → §8 で措置。
- **公式サイドバーは改版で変わる。** 出典のバージョンを本書に記録し、改版時は `renamed` で追随する（`docs/design.md` §6.4）。
- **アプリをまたぐ知識（Blender で作って AE で合成する等）の置き場が1つに定まらない。** メインは主たるアプリに置き、もう一方はサブラベルで付ける（§6）。

## 3. メインラベルの定義（v2）

- 形式は **`<アプリ>/<セクション>` のちょうど2セグメント**。
- 1セグメント（`Blender` だけ）は不可。3セグメント以上（`Blender/モデリング/ベベル`）も**メインには**不可。
- 第二階層は §4・§5 の固定リストからのみ選ぶ。**その場で新設しない**。
- 迷ったときの決め方: **公式ドキュメントのどのセクションにその機能が載っているかで決める**。自分の感覚で決めない。
  - 例: 「マテリアルのバンプ設定」は感覚だと「マテリアル」だが、Blender マニュアル上は Rendering 配下 → `Blender/レンダリング`。
- 例外的に、機能に紐づかない不具合（起動しない・クラッシュする・GPU が認識されない）だけ `…/トラブルシューティング` に置く。**機能に紐づく不具合はその機能のセクションに置く**（Q&A の大半はこちら）。

### 第一階層を増やすとき

第一階層はアプリ単位。増やしてよいのは **公式ドキュメントにサイドバー相当の目次が存在するアプリ**に限る。追加時は本書に第二階層の一覧と出典 URL・取得日を追記してから `labels.json` に登録する。目次のないものを第一階層にすると、v1 と同じ「自分で軸を切る」状態に戻る。

## 6. サブラベルの扱い（v2 で拡張）

サブラベルはメインラベルの制約（2段固定・固定リスト）を受けない。次の3軸を使う。

| 軸 | 用途 | 例 |
|---|---|---|
| **メイン体系の3段目** | 機能の粒度で引きたいとき。**3段目はサブラベル専用** | `Blender/モデリング/ベベル`, `After Effects/エフェクト/カラーコレクション` |
| **もう一方のアプリ／別セクション** | 話題が複数セクションにまたがるとき | メイン `Blender/物理演算` + サブ `Blender/レンダリング` |
| **アプリ直下の形式ラベル**（`section: false`） | アプリ単位で記述の性質を引きたいとき。**セクションではないのでメインラベルにできない** | `Blender/Q&A` |

- **第一階層の補助軸（`形式/…` `横断/…` `状態/…`）は持たない。** v2 の途中まで登録していたが削除した。記述の性質を表したい場合は、第一階層に軸を作らず**アプリ直下の形式ラベル**（下記）を使う。
- 既存 Q&A の frontmatter にある `shortcut` / `version-diff` / `non-destructive` は取り込み時に捨てる。`QandA` だけは `Blender/Q&A` の別名として残す。
- 3段目のサブラベル（`…/ベベル` など）と、アプリ直下の形式ラベルだけが、書きながら増やしてよい枠。ただしレジストリ登録は必須。

### アプリ直下の形式ラベル（`section: false`）

`Blender/Q&A` は2段ラベルだが、公式ドキュメントのセクションではない。そのまま登録するとメインラベルの固定リスト（§4）に混ざってしまうため、レジストリで `"section": false` を付けて固定リストから外す。

- `section: false` のラベルは **サブラベル専用**。メインラベルに指定するとビルドが失敗する
- `section` を指定できるのは**第二階層だけ**（それ以外は元からメインラベルになれない）
- 形式の軸を第一階層（`形式/…`）に戻すのではなく、アプリの下に置く。「どのアプリの Q&A か」が常に決まるため、アプリをまたいだ `形式/Q&A` より絞り込みが素直になる

## 7. データモデルと検証ルール

### 7.1 `meta.json`

```json
{
  "schemaVersion": 2,
  "id": "20260915-xxxx",
  "title": "Ctrl+Bのベベルとベベルモディファイアの使い分け",
  "summary": "…",
  "mainLabel": "Blender/モデリング",
  "subLabels": ["Blender/モデリング/ベベル"],
  "createdAt": "2026-09-15",
  "updatedAt": "2026-09-15",
  "visibility": "private"
}
```

`mainLabel` は配列ではなく**文字列**。「1つしか付かない」を実行時チェックではなく型で保証する。`subLabels` は空配列可。旧 `labels: string[]` は廃止（`schemaVersion: 2`）。

ビルド生成物 `index.json` は `allLabels = [mainLabel, ...subLabels]` を展開して持ち、絞り込みはこれを見る。ラベルツリー実装はメイン/サブを意識しないまま動く。各ラベルには `mainCount`（メインラベルとして付いた件数）を `selfCount` とは別に持たせる。

### 7.2 検証（`npm run build`）

**エラー（ビルドを失敗させる）**

1. `mainLabel` が無い / 空文字 / 配列
2. `mainLabel` が2セグメントでない（1段だけ、または3段以上）
3. `mainLabel` の第一階層が登録済みアプリでない
4. `mainLabel` の第二階層が、そのアプリの固定リスト（§4・§5）に無い
5. `mainLabel` が `subLabels` にも含まれている
6. `subLabels` に重複がある
7. いずれかのラベルがレジストリ未登録（`renamed` で解決できない）

**警告（ビルドは通す）**

8. `subLabels` が空
9. メイン + サブの合計が 8 件以上
10. 第二階層の固定リストのうち、0 件のまま放置されているもの（`scripts/label-ops.ts unused` が拾う。ただし**固定リストは0件でもエラーにしない**。候補として先に全部登録するのが本仕様の前提）

### 7.3 `docs/design.md` §6.2 正規化ルールとの衝突（要改訂）

現行の正規化ルールは本仕様と2点ぶつかる。**レジストリに登録済みの表記は正規化の対象外とする**例外を `lib/labels.ts` に入れて解消する。

| 現行ルール | 衝突 | 対応 |
|---|---|---|
| 規則7「ラテン文字のみのセグメントは小文字に統一」 | `Blender` → `blender`、`3D` → `3d` になってしまう | レジストリ登録済みの正規表記を優先。小文字化は**照合時のみ**行い、保存・表示は登録表記 |
| 規則6「空白は非推奨・警告」 | `After Effects` は公式表記として空白が必要 | レジストリ登録済みのラベルは警告対象から除外 |

## 8. 既存データへの影響

### 8.1 サンプル3ページ

`20260920-19yr`（note001 の使い方）・`20260920-1rp7`（iframe と CSP）・`20260920-2rg2`（SQLite FTS5）は、いずれも Blender / After Effects に属さない。設計検証用に作ったサンプルなので、**削除を推奨**する。残す場合は第一階層に `note001`（このアプリ自身の運用知識）を暫定で足すことになるが、公式ドキュメントを持たない第一階層を認めることになり、§5 末尾のルールを自分で破る。判断は本人に委ねる（未決 L3）。

`content/labels.json` の現行17ラベル（`技術/…` `仕事` `生活` `形式/…` `状態/…`）は**すべて削除**し、§4・§5 の固定リストに置き換える。主題軸（`技術` `仕事` `生活`）だけでなく、補助軸（`形式/…` `横断/…` `状態/…`）も残さない（§6）。

### 8.2 `docs/` の Q&A 11本（取り込み対象）

本仕様で実際に貼れるか検証した。11本すべて、メインラベルが1つに決まった。

| ページ | メインラベル | サブラベル（案） |
|---|---|---|
| Ctrl+Bとベベルモディファイアの使い分け | `Blender/モデリング` | `…/ベベル` |
| ベベル後の編集が大変な問題 | `Blender/モデリング` | `…/ベベル` |
| ボトルと中身（液体）のベベル運用 | `Blender/モデリング` | `…/ベベル` |
| スムーズシェードをかけるタイミング | `Blender/モデリング` | `Blender/レンダリング` |
| ボックス選択で囲んでも選択されない | `Blender/モデリング` | （なし） |
| カーソルに白い丸が付いてくる | `Blender/エディター` | （なし） |
| マテリアルのバンプ設定 | `Blender/レンダリング` | （なし） |
| ワールドで正距円筒図が選べない | `Blender/レンダリング` | （なし） |
| コンポジターにノードの使用がない | `Blender/コンポジティング` | （なし） |
| シーケンサーで秒表示に切り替える | `Blender/ビデオ編集` | （なし） |
| 流体シミュレーションで液体が出ない | `Blender/物理演算` | （なし） |

判断が割れうる2件と、その決め方:

- **「カーソルに白い丸」** — 中身は「サークル選択ツールがアクティブになっている」。選択そのものではなくビューポートのツールバーの話なので `Blender/エディター`。
- **「ボックス選択で囲んでも選択されない」** — 編集モードの選択と X-Ray の話で、公式では Modeling 配下に載る → `Blender/モデリング`。

どちらも「感覚」ではなく「公式のどこに載っているか」で決めた。この決め方自体が §3 のルール。
