SQLite FTS5 で日本語を引く

既定のトークナイザは日本語を分割しない。trigram で引けるようにする方法と、その代償。

状態/検証中 — 手元で実行して確かめていない

何が問題か

FTS5 の既定トークナイザ unicode61 は、英数字以外の文字を区切りとして扱う。 日本語は語の間に空白が無いため、一文がまるごと1トークンになる。 その結果、「知識ベース」で引いても「個人用の知識ベースを作る」にヒットしない。

trigram トークナイザ

SQLite 3.34.0 で追加された trigram は、文字列を3文字ずつ1文字送りで切る。 言語を知らなくても部分一致が引けるようになる。 

CREATE VIRTUAL TABLE pages_fts USING fts5(
  title,
  summary,
  body,
  tokenize = 'trigram'
);

2文字の検索語が引けない

3文字未満の語からはトライグラムが1つも作れない。「東京」「設計」のような2文字語は FTS5 側では扱えないため、短い語は LIKE にフォールバックする設計が必要になる。 trigram 索引は LIKE / GLOB の前方一致以外も加速できるので、この併用は無駄にならない。

索引の大きさと detail オプション

トライグラムは1文字ずつずらして切るため、トークン数は概ね本文の文字数と同じになる。 索引は本文より大きくなりやすい。効くのは detail と contentless。

設定 効果 失うもの
detail=full（既定） 位置情報あり —
detail=column 索引が小さくなる フレーズ検索・NEAR
detail=none 最も小さい フレーズ検索・NEAR・列単位の絞り込み
content='' 本文を二重に持たない 列の値を返せない・再構築できない
content='pages' 実テーブルを正として参照 同期はトリガで自分で保つ必要がある

引くときの形

SELECT
  p.id,
  p.title,
  snippet(pages_fts, 2, '<mark>', '</mark>', '…', 12) AS excerpt,
  bm25(pages_fts, 10.0, 5.0, 1.0) AS score
FROM pages_fts
JOIN pages AS p ON p.rowid = pages_fts.rowid
WHERE pages_fts MATCH ?
ORDER BY score      -- bm25 は小さいほど良い
LIMIT 20;

bm25() の引数は列ごとの重み。タイトルと summary を本文より重くすると、 知識ベースの検索としては素直な順序になる。

note001 で使うとしたら

このアプリは DB を持たない静的構成なので、FTS5 をそのまま使う道は無い。 ただし考え方はそのまま効く。全文検索（Phase 3）では、ビルド時に本文からテキストを抽出して トライグラムの索引を JSON で作り、クライアント側で引く形になる。 2文字語の扱いと索引サイズという2つの問題は、実装が変わっても同じ形で出てくる。

確かめるべきこと

  • trigram の索引サイズが実際の日本語本文で何倍になるか
  • 2文字語のフォールバックを含めた検索体験が許容できるか
  • クライアント側で引く場合、索引 JSON をどこまで分割・遅延読み込みすべきか
